# Analysis Methodology and Rules

Status: **Day 13 - full analysis pipeline implemented, unit-tested, and verified against event_log.csv.** Any change goes through Member 2 and is announced in the team channel.

## 1. Core Analysis Questions
Our Python analysis scripts answer the following business questions using the event log data:
* **Process Discovery:** What is the most frequent clinical pathway patients take from Registration to Discharge?
* **Bottleneck Identification:** Which consecutive activities have the longest average transition times (wait times)?
* **Rework Metrics:** How often do patients experience a "loop-back" (e.g., returning to Triage after an X-Ray) or an immediate repeat?
* **Throughput & Conformance:** What is the average total time a patient spends in the hospital system, and how closely do actual pathways follow the hospital's ideal 6-step clinical pathway?

## 2. Input Assumptions
* The input is `data/event_log.csv`, generated by Member 1. One row per event.
* Columns: `case_id`, `activity`, `timestamp` (required) and `resource`, `shift` (optional).
* `timestamp` format is `YYYY-MM-DD HH:MM:SS`, 24-hour clock, no timezone.
* Activity names are exactly those in `src/common/schema.py`: `Registration`, `Triage`, `Doctor Consultation`, `X-Ray`, `Doctor Review`, `Discharge`.
* All data is synthetic and has passed Member 1's validation checks (`10/10 PASS`); the rules below act as an additional defensive safety net.

## 3. Rules for Sorting and Calculating Time

| # | Rule |
|---|------|
| R1 | **Sorting.** Sort by `case_id`, then by `timestamp` (oldest first) before any analysis. The row order in the file is never trusted. Events with an identical timestamp keep their recorded order. |
| R2 | **Cases.** A case is all rows with the same `case_id`. Time is never calculated across two different cases. |
| R3 | **Transition time.** The difference in minutes between the timestamp of the current event and the timestamp of the immediately preceding event of the same case. It is kept as a decimal (2.5 = 2 min 30 s), and the full date and time are used, so a journey that crosses midnight is handled correctly. |
| R4 | **First event.** The first event of a case has no preceding event, so its transition time is left **empty (`NaN`), never 0**, and it is excluded from every average. |
| R5 | **Attribution.** A transition time belongs to the pair *(previous activity -> current activity)*. Averages are reported per pair, never per activity alone, because arriving at `Doctor Consultation` takes a different time after `Triage` than after `X-Ray`. |
| R6 | **Wording.** The log has one timestamp per event, so the gap contains waiting and the activity itself. We call it *transition time* (the project "wait time"). |
| R7 | **Case duration (throughput).** Last timestamp minus first timestamp of the case, in minutes. The average is taken over all included cases. |
| R8 | **Complete cases only.** After sorting, a case must start with `Registration` and end with `Discharge`. Any other case is excluded from all metrics and listed in a warning. |
| R9 | **Unusable rows.** A row with a missing `case_id`, a missing `activity` or an unreadable `timestamp` is skipped with a warning. Values are never guessed or filled in. |

### Rework definitions
Repeat and loop-back never overlap:

| # | Definition |
|---|------------|
| R10 | **Repeat:** a transition from an activity to itself, e.g. `X-Ray -> X-Ray`. |
| R11 | **Loop-back:** a transition to an activity that already occurred earlier in the case and is not an immediate repeat, e.g. `Triage -> Doctor Consultation -> X-Ray -> Triage`. Every such transition counts once. |
| R12 | **Rework rate:** cases with at least one loop-back divided by all included cases. |

### Worked example (`CASE-0001`)

| # | Activity | Timestamp | Previous activity | Transition (min) | Note |
|---|----------|-----------|-------------------|------------------|------|
| 1 | Registration | 08:00 | - | empty | first event (R4) |
| 2 | Triage | 08:10 | Registration | 10 | |
| 3 | Doctor Consultation | 08:35 | Triage | 25 | |
| 4 | X-Ray | 08:50 | Doctor Consultation | 15 | |
| 5 | Triage | 09:20 | X-Ray | 30 | loop-back (R11) |
| 6 | Doctor Consultation | 09:40 | Triage | 20 | loop-back (R11) |
| 7 | Doctor Review | 10:10 | Doctor Consultation | 30 | |
| 8 | Discharge | 10:25 | Doctor Review | 15 | |

Case duration (R7): `08:00` to `10:25` = **145 minutes**. A repeat looks like `X-Ray` at `09:50`, then `X-Ray` again at `10:20` (`30 min`).

### Output files
All six files in `outputs/` are regenerated by running the scripts in `src/analysis/` and are never edited by hand.

| File | Made by | Contents |
|------|---------|----------|
| `outputs/event_transitions.csv` | `src/analysis/calculate_metrics.py` | Every included event with `previous_activity` and `transition_time_minutes` (empty for first events). |
| `outputs/bottleneck_metrics.csv` | `src/analysis/find_bottlenecks.py` | One row per pair: `from_activity`, `to_activity`, `count`, `avg_minutes`, `median_minutes`, `max_minutes`, `rank`. Rank 1 is the longest average; equal averages share a rank. |
| `outputs/process_paths.csv` | `src/analysis/discover_process.py` | Unique patient pathways ranked by frequency (`case_count`, `pct_cases`), `step_count`, throughput duration (`avg_duration_minutes`, `median_duration_minutes`), `has_repeat`, and `has_loopback`. |
| `outputs/repeat_loop_metrics.csv` | `src/analysis/discover_process.py` | Repeat (R10) and loop-back (R11) transition pairs with `transition_count`, `cases_affected`, `pct_cases_affected`, and wait-time stats. |
| `outputs/process_map_edges.csv` | `src/analysis/discover_process.py` | Directed graph edge table (`from_activity`, `to_activity`, `count`, `case_count`, `pct_cases`, wait-time stats, `is_ideal_edge`, `edge_type`, `loopback_count`) for the process map. |
| `outputs/conformance_summary.csv` | `src/analysis/check_conformance.py` | Pathway-level conformance comparison against `IDEAL_PATH` (`is_conformant`, `deviation_type`, `skipped_steps`, `skipped_count`, case counts, and durations). |

## 4. Conformance Checking
* The actual paths taken by patients are compared against the `IDEAL_PATH` defined in `src/common/schema.py`: `Registration -> Triage -> Doctor Consultation -> X-Ray -> Doctor Review -> Discharge`.
* Any deviation (`skipped_steps`, `out_of_order`, `extra_steps`, `repeat`, or `loop_back`) is flagged as non-conformant, and non-conformant journeys are further split into deviations without rework vs. journeys with repeats/loop-backs.
